二、项目目标与原则

2.1 技术目标

  • 球队、分类、商品页面URL与内容映射准确率达到100%。
  • 无效球队、分类和商品ID返回真实404或410，不再静默跳转New Arrivals。
  • 缓存命中情况下，首页及核心落地页TTFB控制在1秒以内。
  • 核心页面P75指标：LCP ≤ 2.5秒、INP ≤ 200毫秒、CLS ≤ 0.1。
  • 首页HTML第一阶段控制在500KB以内。
  • 下单和支付接口具备幂等、防重复提交、异常恢复与可追踪日志。

2.2 SEO与GEO目标

  • 首页、分类页、球队页和商品页建立规范的H1/H2层级。
  • Product、Offer、BreadcrumbList等结构化数据覆盖率达到95%以上。
  • Sitemap仅保留返回200的Canonical标准页。
  • 建立语义化URL、301重定向、hreflang及多语言索引规则。
  • 商品描述与分类介绍在服务端HTML中可抓取。
  • 上线根目录/llms.txt，并为首页、分类、球队、商品、尺码、物流与退换货页面建立清晰、可引用的GEO内容结构。
  • 建立品牌、商品、价格、库存、配送和退换货信息的一致性机制，减少AI搜索引用过期或冲突内容。

2.3 转化目标

五、网站性能优化

5.1 后端与TTFB

TTFB偏慢通常不是单一前端文件造成，应优先从服务端渲染、数据库、缓存和服务器区域定位。

检查项研发动作验收标准
数据库慢查询记录查询耗时；检查N+1；为team_id、category_id、slug、status、locale、inventory_status等字段补索引。核心页面数据库查询P95下降，慢查询有可追踪日志。
服务端串行请求首屏必要数据并行加载；评价、推荐、非首屏模块异步化。首屏不再等待推荐和评价接口完成。
页面缓存首页、球队、分类和商品主体使用CDN或边缘缓存；后台更新主动失效。缓存命中TTFB ≤1秒；缓存更新不超过设定窗口。
地理距离评估源站区域、CDN节点与主要市场网络延迟。主要市场网络P75显著改善。

5.2 HTML体积

  • 首屏HTML只返回当前视口和首屏交互必需的数据。
  • 禁止把完整球队、商品、评价、多语言字典和推荐数据序列化进HTML。
  • 非首屏模块滚动接近时再加载。
  • 删除重复JSON、重复内联样式和开发环境调试数据。
  • 第一阶段将首页HTML降到500KB以内，并持续追踪压缩后体积。

5.3 JavaScript与CSS

JavaScript
按路由拆包；营销、客服、评论和推荐延迟加载；删除重复工具库；限制第三方脚本主线程占用；建立Bundle预算。
CSS
提取Critical CSS；删除未使用样式；统一Button、Input、Card、Modal组件；避免加载当前路由不需要的主题文件。

5.4 图片与列表

  • Hero图使用响应式尺寸，移动端不下载桌面超大图。
  • LCP图片设置高优先级，非首屏图片懒加载。
  • 商品图固定宽高，降低CLS；评估AVIF与CDN动态裁切。
  • 分类页每次加载24—40件商品，使用游标分页。
  • 提供可抓取分页URL，并恢复浏览器返回后的滚动位置。
  • 筛选或排序变化时取消旧请求，避免并发和界面闪烁。

5.5 API稳定性

  • GET请求设置超时，并对可安全重试的请求自动重试1—2次。
  • 下单和支付POST请求使用幂等Key，禁止普通重复提交。
  • 区分网络异常、服务器异常、库存不足和业务校验失败。
  • 错误提示对用户可理解，后台保留错误码、订单号、接口和追踪ID。
  • 接口失败率超过阈值时自动告警。

六、SEO与GEO技术优化

6.1 路由与软404

访问 /team/Liverpool/98
1. 根据ID查询球队
2. 查询标准Slug
3. ID不存在：返回404
4. ID存在、Slug错误：301到标准URL
5. Slug与ID一致：返回200并展示对应球队内容

严禁无效ID跳转到New Arrivals并返回200。该处理会制造软404和重复内容，稀释站点权重并浪费广告流量。

6.2 URL规范

/team/real-madrid/category/kids-soccer-jerseys/category/retro-soccer-jerseys/product/real-madrid-home-jersey-2026

现有带ID的URL可以阶段性保留，但必须校验Slug。对/category/tag-428等无语义URL，建立新URL、逐条301、更新站内链接和Sitemap，并保留重定向至少12个月。

6.3 页面语义层级

页面H1建议H2示例
首页Soccer Jerseys Online – Club, National Team & Custom JerseysWorld Cup 2026 Jerseys、Popular Club Jerseys、Custom Soccer Jerseys
球队页Real Madrid Soccer JerseysHome、Away、Kids、Retro Jerseys
分类页Kids Soccer JerseysPopular Teams、Size Guide、Customization
商品页完整商品名称Product Details、Size Guide、Reviews

6.4 结构化数据

  • 商品页：Product、Offer、BreadcrumbList；评价真实可靠后再输出AggregateRating和Review。
  • 分类和球队页：BreadcrumbList、ItemList。
  • 首页：Organization、WebSite、SearchAction。
  • FAQ Schema只能对应页面上真实展示的FAQ。
  • 结构化数据通过自动测试校验，避免价格、库存和页面显示不一致。

6.5 Canonical、Sitemap与多语言

  • Sitemap只包含200状态的标准URL；301、404和noindex页面不得进入。
  • 筛选和排序参数不生成大量可索引重复页面。
  • Canonical指向当前语言和当前实体的标准URL。
  • 多语言页面建立互相对应的hreflang和x-default。
  • 商品删除后自动从Sitemap移除；有替代品则配置301，无替代则404或410。

6.6 服务端可抓取内容

商品DESCRIPTION、CARE和SPECIFICATIONS应在首次HTML中输出，而不是仅依赖客户端异步请求。分类页增加150—250字真实介绍，放在商品列表下方并支持折叠。

6.7 GEO优化定位与实施边界

GEO（Generative Engine Optimization）的目标，是让Google AI功能、Microsoft Copilot及其他生成式搜索系统更容易找到、理解、核实并引用网站内容。其基础仍然是可索引的页面、清晰的文本、准确的结构化数据、良好的内部链接和可信的事实信息，不应被理解为单独堆叠“AI关键词”。

实施边界：llms.txt目前应作为辅助发现与内容导航文件，不替代robots.txt、Sitemap、Canonical、hreflang或页面级结构化数据，也不保证任何AI系统一定抓取或引用。
  • 所有提供给AI系统的价格、库存、配送、退换货和定制规则，必须与用户页面及后台数据一致。
  • 关键事实优先用清晰文本和表格呈现，不能只存在于图片、轮播图、弹窗或客户端脚本中。
  • 页面先直接回答用户问题，再补充商品列表、品牌故事和营销内容。
  • 禁止为了GEO批量生成重复、空洞或无法核实的球队历史、商品评价和FAQ。
  • 避免使用无法证明的“official”“authentic”等表述；产品版本、授权关系和商品属性必须准确。

6.8 部署根目录 llms.txt

在网站根目录提供https://www.gojersey.co/llms.txt，使用UTF-8纯文本和Markdown结构，返回200状态码，不经过登录、Cookie弹窗或多次重定向。文件由CMS配置生成，并由SEO/GEO负责人维护。

要求实施说明验收标准
文件位置固定为根目录/llms.txt直接访问返回200
格式Markdown；一个H1站点名称、简短说明、H2分组和带描述的标准链接UTF-8、无HTML模板和脚本
链接范围只放Canonical、公开、长期有价值的首页、分类、球队、指南和政策页不得包含404、301链、参数页或用户私有页面
更新方式URL迁移、政策或重要分类变化时自动重新生成每周自动检测失效链接，每月人工复核
安全边界不得包含订单、客户、支付、后台、内部接口和未公开商业数据安全扫描无敏感信息

七、下单流程优化

保留现有访客结账和加购确认优势，参考成熟Shopify主题，将商品选择、费用确认、购物车和单页结账整合成一条更短、更透明、异常可恢复的购买链路。

7.1 将原三步结算流程缩短为两步

原系统将用户拆分到“购物车—地址与物流选择—支付”三个独立步骤。每增加一次页面跳转和确认，都可能造成移动端加载等待、信息重复填写、返回修改困难以及中途退出。参考Shopify的结账体验，建议将地址、配送方式和支付方式整合进同一个结账页面，把用户可感知的下单流程缩短为两步。

流程页面步骤主要问题或改进
原系统购物车 → 地址/物流选择 → 支付三个独立页面，页面跳转多；地址和物流页容易形成额外流失点；移动端返回修改商品或地址成本较高。
优化后购物车 → 结账在同一结账页完成联系信息、地址、配送方式和支付；减少一步跳转，缩短下单时间并提升结账完成率。
 
原流程：购物车 → 地址与物流选择 → 支付

目标流程：购物车 → 结账
                    ├─ 联系信息
                    ├─ 收货地址
                    ├─ 配送方式
                    └─ 支付方式

研发实施要求

  • 购物车点击“Checkout”后直接进入统一结账页，不再设置独立的地址物流中间页面。
  • 结账页按Contact、Delivery、Payment三个区域组织，但用户仍停留在同一页面完成操作。
  • 填写国家、州省、邮编后，配送方式和费用在当前页面即时刷新，不整页跳转。
  • 用户修改地址时只重新计算物流和税费，不清空商品、优惠码、定制信息和支付选择。
  • 移动端采用折叠分区或连续表单，底部持续展示订单总价和主操作按钮。
  • 快捷支付可从购物车或结账页直接发起，但必须保留地址校验、金额校验和订单幂等。
  • 对“购物车进入结账率、结账页退出率、完成支付耗时、结账完成率”分别建立优化前后对比。
核心目标：减少一个用户可感知的页面步骤，而不是简单隐藏页面。地址、物流、税费、优惠和支付仍需完整校验，只是集中在同一结账界面内完成。

7.2 推荐购买链路

商品详情页
→ 选择版本、尺码、定制内容
→ 实时显示总价与送达日期
→ 加入购物车
→ 购物车抽屉
→ 购物车页或直接结账
→ 统一结账页（地址 + 物流 + 支付）
→ 订单成功页

7.3 商品详情页

  1. 图片、标题、真实评分和评价数。
  2. 单件价格为主，阶梯价为辅。
  3. 版本选择和球迷版/球员版差异说明。
  4. 尺码选择、尺码表和缺货提示。
  5. 姓名、号码、Patch定制。
  6. 实时显示商品价、每项定制费和当前合计。
  7. 显示定制商品退换货限制并要求用户核对拼写。
  8. 根据国家和物流方式计算预计到达日期区间。
  9. 加入购物车按钮及移动端悬浮操作栏。
定制金额必须以后端计算为准。前端仅负责交互展示；后端重新校验商品、尺码、定制选项、折扣和最终金额，防止前端篡改。

模块必须展示

物流根据当前日期显示预计送达区间。
操作修改、删除、查看购物车、立即结账。

7.5 购物车页面

  • 提前说明运费和税费，不允许到支付前最后一步才出现额外费用。
  • 包含定制商品时，显示不可无理由退货提示。
  • 推荐模块只展示同球队、同赛季、相关品类或后台手动绑定商品。
  • 排除贺卡、礼品卡、当前已购、缺货和国家不匹配商品。
  • 移动端结账按钮保持清晰可见，但不得遮挡优惠和错误提示。

7.6 统一结账页

1. Contact
2. Delivery
3. Payment
  • 允许访客结账，不强制注册。
  • 快捷支付放在顶部，普通表单保持清晰。
  • 国家变化后自动调整省州、电话和邮编规则。
  • 表单错误行内提示并自动聚焦，刷新或支付失败后保留内容。
  • 桌面端订单摘要持续可见；移动端提供清晰的展开入口。
  • 优惠码默认折叠，结账页不展示无关推荐和营销弹窗。

7.7 支付与订单状态机

cart → checkout_created → payment_pending → payment_processing
→ paid / payment_failed / cancelled / refunded / partially_refunded
  • 支付接口使用幂等Key，防止双击和重复回调生成重复订单。
  • 订单金额在服务端重新校验。
  • 支付成功以支付网关回调为准，不能只依赖前端成功页跳转。
  • 支付失败后保留购物车和地址，允许切换支付方式再次尝试。
  • 支付回调失败建立自动补偿任务和人工处理队列。
